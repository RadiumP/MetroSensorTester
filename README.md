# Metro Sensor Tester

原生 Kotlin/Android 地铁与轻轨传感器采集原型。

## 功能

- 线性加速度（无对应传感器时使用加速度计高通滤波）
- 罗盘磁北方位（优先旋转矢量，回退加速度计+磁力计）、八方向与校准状态
- 可选粗略位置磁偏角修正真北，并标记地铁环境磁场干扰
- 陀螺仪、磁力计原始 XYZ 与磁场强度、气压计
- Android `AudioRecord` 麦克风 RMS、峰值、输入设备与录音状态
- PCM 近零异常检测、1 秒恢复确认和限频安全重启
- 检测 Android 音频框架系统静音，并记录 AudioRecord 读取与路由诊断
- 固定三区间迟滞启动，并使用最近 3 分钟有效数据平滑生成动态阈值
- 列车运行/停站与玩家活动独立判断
- 前台服务、常驻通知和 PARTIAL_WAKE_LOCK 后台采集
- 人工标记运行和停站
- 使用系统文件选择器导出 UTF-8 CSV（状态字段 schema v5，保留旧字段并追加罗盘/音频诊断字段）

## 打开与运行

1. 使用 Android Studio 打开本目录并等待 Gradle Sync。
2. 用 USB 连接手机并允许 USB 调试。
3. 选择手机后点击 Run。
4. 首次开始采集时允许麦克风和通知权限；粗略位置权限仅用于真北修正，可拒绝；精确位置权限用于下文"GPS 位准"的校准测试，同样可拒绝——拒绝后校准测试必然不通过，退回纯麦克风/磁场判定，不影响其余功能。

项目使用 JDK 17、compileSdk 34，最低支持 Android 8.0（API 26）。

## 状态判定

- 固定启动阈值：RMS `<= 0.0014` 为停站候选，RMS `>= 0.0018` 为运行候选，中间区域保持稳定状态并清除候选计时。
- 停站候选连续 3 秒后切换为停站；运行候选连续 1.75 秒后切换为运行。
- 分别使用最近 3 分钟内"停站"和"运行"各自状态下的有效非零样本计算阈值（停站取本状态 P75、运行取本状态 P25），而不是把两种状态混合排序后取一个整体分位数——避免某一状态（例如长时间停靠）样本占多数时，把另一状态的阈值带偏。两种状态样本数都达到最少数量后才启用动态阈值。
- 动态停站阈值限制在 `0.0005..0.0016`，运行阈值限制在 `0.0010..0.0030`（2026-09-02 前分别是 `0.0008..0.0016` / `0.0016..0.0030`，因为一趟地面轻轨整体噪音水平偏低——运行时 RMS 中位数只有约 0.0013，够不到旧的运行阈值下限，即使动态阈值本该能追上去也追不到——放宽下限）；首次启用直接采用计算值，此后每 5 秒按计算值缓慢平滑一次并保留最小迟滞间隔。
- 长时间只有单一列车状态时冻结动态阈值，避免继续漂移。
- 判定所用的时间基准是开机后单调递增的 `elapsedRealtime`，不受手机在隧道失联后重新联网校时导致的墙钟跳变影响；仅 CSV 里的 `ts` 列使用墙钟时间用于人类可读的时间戳。
- 玩家活动独立使用加速度 RMS（`0.40 m/s²`）或陀螺仪 RMS（`15 °/s`）判断，不会改变 `train_state`。
- 每个采集 tick 额外记录 `mic_crest_factor`（`mic_peak / mic_rms`）和 `mic_chime_candidate`（该 tick 是否疑似捕捉到进出站固定广播提示音）：正常车厢环境音的峰值/RMS 比值大致在 2.3–4.5 之间，而报站提示音这类短促响动在整窗 RMS 里几乎不留痕迹、却会让瞬时峰值明显蹿高，因此峰值/RMS 比值异常升高（`>= 8`，且峰值本身不能太小，`>= 0.008`，避免噪声地板附近的比值误判）是识别它的低成本信号。目前这两个字段只用于记录，**不参与** `train_state` 的判定逻辑。
  - 实地测试（2026-08-28，用"广播"按钮标出 4 次报站提示音 + 3 次开关门报警音）：`mic_crest_factor` 对报站提示音基本不起作用（4 次全部低于阈值，最高只到 4.4）——提示音是持续 1-2 秒的语音，会拉高整窗 RMS 而不是只拉高瞬时峰值，不符合"峰值远高于均值"的假设。对开关门报警音稍微有戏（3 次里 2 次达到 6.3-7.1，接近但没到 8 倍阈值），但样本太少，尚未调整阈值。
- 因此额外记录 `mic_baseline_rms` / `mic_rms_bump_ratio` / `mic_rms_bump_candidate`：把当前 tick 的 RMS 和最近一段安静基线（`now - 6000ms` 到 `now - 1000ms` 之间样本的中位数，样本数不足 8 个时不计算）比较，涨幅达到 `1.8` 倍即标记为疑似命中。这个指标是冲着"提示音持续拉高整窗 RMS"这个特点设计的，对报站提示音和开关门报警音理论上都适用，但实测発現：**只有在最近基线本身安静（比如已经停站）时才会看到明显涨幅（1.5–3.3 倍），一旦车厢已经因为运行而变吵，两种声音都会被环境噪音盖过，涨幅趋近于 1.0 倍**——这是物理上的天花板，不是阈值没调好。同样目前只记录，不参与 `train_state` 判定；`1.8` 倍这个阈值还需要更多实地数据验证。
- 每个采集 tick 还记录 `magnet_magnitude_jitter`：当前磁场强度 `magnet_magnitude_ut` 相对上一个有效样本的绝对变化量。物理原理跟麦克风、加速度计都不同——它捕捉的是列车牵引电机工作时产生的电磁干扰对磁场强度本身的扰动，跟手机被乘客手持转动导致的方向变化（会污染融合后的 `compass_heading_deg`，但不影响原始磁场强度）无关。截至 2026-08-30 累计 11 趟真实数据，运行时抖动中位数始终高于停站时（1.49–4.97 倍），但单点噪声偏大——大多数趟次运行 P25 和停站 P75 的分位数区间仍有重叠，不能直接拿瞬时值卡阈值判定。
- 因此 `magnet_magnitude_jitter` 已经作为"辅助确认"信号接入判定逻辑（2026-08-31）——**麦克风 RMS 仍是唯一的主判定信号**，磁场只是在麦克风已经给出候选方向（停站候选/运行候选）之后，加快或放慢确认计时，不会单独触发状态切换：
  - `magnet_jitter_smoothed`：对 `magnet_magnitude_jitter` 取最近 4 秒窗口（至少 4 个样本）的中位数，抹平单点噪声。
  - `magnet_candidate_state`：磁场通道自己的候选状态（`运行`/`停站`/空）。用跟麦克风一样的"本状态最近 3 分钟历史 P75(停站)/P25(运行)"动态分位数技术算阈值，样本不够时退回固定阈值（停站 `<= 1.2`，运行 `>= 2.0`，取自 11 趟数据的经验范围）。
  - `magnet_assist_note`：本 tick 磁场对麦克风确认计时的调整方式——`agree`（磁场候选跟麦克风候选方向一致）把所需确认时长缩短到 0.6 倍（停站 3000ms→1800ms，运行 1750ms→1050ms，并设 500ms 下限防止瞬间切换）；`disagree`（方向相反）拉长到 1.4 倍（停站→4200ms，运行→2450ms）；`none`（磁场没有数据或处于中间模糊区）不调整，维持原有固定时长。
  - 这个设计的意图是把磁场当作"降噪辅助"而不是"独立判据"：即使磁场信号在某一趟车上表现异常，最坏情况也只是确认变慢/变快一点，不会导致误判 `train_state` 本身——误判的唯一来源仍然是麦克风信号。后续如果磁场信号在更多数据上持续可靠，可以考虑把它提升为更强的融合角色。
- **磁场独立触发（2026-09-02，2026-09-05 由"连续不间断"改为"滚动窗口多数票"）**：上面的辅助确认有个结构性缺口——它只能在麦克风自己已经给出候选方向之后加速/减速确认，麦克风如果压根没建立候选（比如整个环境噪音水平太低，运行时 RMS 从来没到过运行阈值），磁场再准也插不上手。实地测试中一趟地面轻轨正是这样：全程 1692 个采样点里 97%+ 被误判成"停站"，因为运行时 mic RMS 中位数（0.0013）跟停站时（0.0009）几乎没区别（分离度只有 1.4x），而同一趟车里磁场抖动依然有 1.6x 的分离度、方向也一直正确。因此新增一个兜底触发，不管麦克风那一刻在说什么，直接由磁场把状态切过去（`magnet_assist_note=trigger`）。
  - 最初的实现要求 `magnet_candidate_state` **连续不间断** `15000ms` 都跟当前稳定状态相反才触发。2026-09-05 用一趟新地铁实地数据发现这个要求太严：其中一段被误判"停站"长达 137 秒，20 秒滚动窗口里"运行"候选票占比稳定在 93%–100%，方向明显正确，但受限于磁场信号本身会偶尔闪回（不是持续单调），整段里最长的一次连续不间断"运行"候选也只有 4.5 秒，永远够不到 15 秒门槛——磁场信号是真实有效的，只是原来的"连续不间断"条件对这种间歇性信号太苛刻，导致触发器实际上从未生效。
  - 因此把触发条件从"连续不间断"改成"滚动窗口多数票"：维护最近 `MAGNET_INDEPENDENT_WINDOW_MS`（20 秒）内每个 tick 的磁场候选方向投票，累计满 `MAGNET_INDEPENDENT_MIN_SAMPLES`（20 票）后，只要多数方向的占比达到 `MAGNET_INDEPENDENT_MAJORITY_RATIO`（75%）且跟当前稳定状态相反，就直接触发切换并清空票池重新计票。20 秒窗口比麦克风侧任何一种确认时长（包括反对时拉长后的 4200ms/2450ms）都长得多，仍然只作为"麦克风完全失效场景"下的最后兜底，不影响麦克风正常工作时的判定节奏。触发之后该状态下的麦克风样本会正常进入 `mic_history`，后续麦克风自己的动态阈值也能借着这批新样本重新校准，理论上之后麦克风就能自己接管，不需要每次都靠磁场硬切。

## 磁场精度判断与纯磁场实测配置（2026-09-10）

对 09-05 / 09-06 / 09-08 三趟数据分析后加入。核心发现是：磁场抖动信号本身带真实区分度（09-08 全程 `magnet_jitter_smoothed` 中位数 停站 1.47 / 运行 2.41），但**同一台手机不同趟之间的信号强度差异极大**，09-06 那趟整趟 P90 只有 0.85，从未越过 `MAGNET_MOVING_JITTER_THRESHOLD`（2.0），也就是磁场通道全程只可能输出"停站"（实际输出 停站 2706 次 vs 运行 134 次），等于是个坏掉的信号源却仍在参与判定。

- **精度判断为什么不能照抄 GPS 那套**：GPS 有每个定位点自带的 `accuracy`（米）可以直接卡阈值，磁场没有等价物。看起来最像的 `SensorManager` 精度等级（0 不可靠 ~ 3 高）实测**完全不能用作依据**：09-06 那趟 90% 的样本精度等级都是 3（最高），信号却是废的。所以精度等级只记录进 CSV（新增 `magnet_accuracy` 字段，且和原有 `compass_accuracy` 分开，后者在磁力计没上报时会退回用旋转矢量的等级），不参与判定。
- **实际的判据是"能不能同时够到判定带的两侧"**：持续累积平滑后的抖动样本，样本数达到 `MAGNET_CALIBRATION_MIN_SAMPLES`（60）后每帧结算一次，要求观测到的 P10 `<=` 停站阈值 **且** P90 `>=` 运行阈值——即这台手机这趟车的抖动分布确实横跨了自己的判定带，两种结论都有可能产出。
- **不能用固定长度窗口**：和 GPS 精度不同，磁场的区分度在发车前根本测不出来——车还停在站台上时抖动分布本来就窄，"窄"意味着"还没开动"而不是"传感器不行"。所以这个测试是开放式的：**满足条件即刻通过**，只有拖到 `MAGNET_CALIBRATION_MAX_WINDOW_MS`（180 秒）都没满足才判"不可用"。用三趟真实数据把真实引擎跑一遍回放（不是另写的模拟脚本）：09-05 在 28.8 秒判"可用"，09-08 在 16.0 秒判"可用"，09-06 判"不可用"且全程没能翻盘。
- **磁场自己的确认窗口**：通过之后磁场不再只是麦克风的辅助，而是走一套自己的候选/确认状态机，`MAGNET_STOP_CONFIRMATION_MS`（4000）/ `MAGNET_MOVING_CONFIRMATION_MS`（3000）。这两个数是拿 09-05/09-08 扫出来的：2000/1500 时纯磁场分类器会产生 91/105 次切换、两趟各有 12 段短于 5 秒（肉眼可见的抖动），4000/3000 收敛下来，5000/4000 能把短段清零但代价是少掉约三分之一的切换。定了 4000/3000 之后用真实引擎回放两趟：09-05 得到 50 次切换（原融合逻辑记录的是 51 次）、只有 3 段短于 5 秒、中位段长 41.4 秒；09-08 得到 92 次切换（原融合 116 次）、同样只有 3 段短于 5 秒、中位段长 19.2 秒。实地测试若仍有抖动就往 5000/4000 调。注意这是叠加在 `MAGNET_SMOOTHING_WINDOW_MS`（4 秒中位数平滑）之上的，所以端到端反应一次真实换态要好几秒。
- **本次实测配置**：`MIC_DECISION_ENABLED_DEFAULT = false`、`MAGNET_PRIMARY_ENABLED_DEFAULT = true`，即暂时关掉麦克风判定、让磁场单独扛，用来隔离评估磁场通道的真实能力。麦克风依然在采样、依然写进 CSV、依然累积自己的动态阈值历史，只是不能改变 `train_state`，所以一趟纯磁场的数据事后仍然可以拿来和麦克风通道对比。两个开关翻回去（mic true / magnet false）即完全恢复原来的"麦克风主判 + 磁场辅助"逻辑。优先级为 GPS > 磁场 > 麦克风。
- **新增 CSV 字段**：`magnet_calibration_status`（校准中/可用/不可用）、`magnet_calibration_low_jitter`、`magnet_calibration_high_jitter`（判据用的两个观测分位数）、`magnet_stop_candidate_elapsed_ms`、`magnet_moving_candidate_elapsed_ms`、`magnet_accuracy`、`magnet_stop_confirmation_ms`、`magnet_moving_confirmation_ms`、`mic_decision_enabled`、`magnet_primary_enabled`。`magnet_assist_note` 新增取值 `primary`，表示这一帧是磁场直接定的状态。
- **实地验证结果（2026-09-11，15.7 分钟）**：第一趟真实的纯磁场采集，结论是这套判定目前最准。校准在 16.0 秒通过（观测到 P10=0.60 / P90=4.20，横跨判定带很充分），之后全程 `可用`，一次 `magnet-signal-lost` 都没出现，最终 14 次切换、7 个停站段（52.6 / 48.3 / 50.1 / 13.6 / 51.7 / 52.0 / 9.1 秒），运行段 68~131 秒。乘车时的主观观察是**车一停状态就跟着转**，这是麦克风做不到的。
- **为什么比麦克风准（拿同一趟数据对照跑出来的）**：麦克风通道在纯磁场模式下依然在采样和记录，所以可以拿同一份 CSV 用麦克风逻辑重跑一遍做对照。两者逐帧一致率 86.9%，但分歧方向高度一致、不是随机噪声：进站时麦克风比磁场**早 8~20 秒**就判停站（-20.4 / -8.4 / -8.1 / -13.6 秒，仅一次持平），出站时又**晚 2~9 秒**才判运行（+9.1 / +3.8 / +6.3 / +3.5 / +9.1 / +2.0 秒），即麦克风把"运行"这一段两头都削短了。看波形能看出原因是**惰行**：列车提前断电滑行进站，车厢噪音先安静下来但车还在动（784~798 秒那段麦克风 RMS 已跌到 0.0009 判停站，磁场抖动还稳在 2.1~3.0，直到 798 秒掉到 0.38 才切），出站同理，起步头几秒车厢还没吵起来。反方向的分歧只有一处（531~545 秒磁场判停站而麦克风判运行），当时 mic_rms 飙到 0.014~0.020，是制动/到站瞬态把麦克风带偏，磁场同样没被骗。
- **硬件精度等级不可用这件事又被验证了一次**：这趟的 `magnet_accuracy` 明显比 09-08 那趟差（等级 3 只占 43% 对 73%，还有 591 帧是 0"不可靠"），通道表现却是最好的一趟。再次确认这个等级和磁场通道能不能用没有关系，不能拿来当判据。
- **待确认**：这趟 `mark` 列全空（没有按标记），所以上面全部是"磁场对麦克风的相对比较 + 物理上的合理性推断"，不是对照地面真值量出来的精度。其中 13.6 秒那个停站段是唯一可疑的短段（末尾 9.1 秒那段是录制结束截断，不算），需要真值才能确认是真的临时停车/信号等待还是一次误判。下一趟测试会用广播标记逐站打点进站和出站，届时可以直接量出延迟秒数和有没有漏判，再回头校准 `MAGNET_STOP_CONFIRMATION_MS` / `MAGNET_MOVING_CONFIRMATION_MS`。另外 `ambiguous-hold` 占 20.7%，这些帧只是保持原状态不翻转，不影响结果。

- **反例：磁场环境被污染的一趟（2026-09-12，6.8 分钟）**：这趟用广播标记逐站打了点，第一次有了地面真值（标记时刻交替解读为停站/出站，得到 3 个完整停站 31.5 / 41.5 / 41.8 秒，3 段运行 106.5 / 81.5 / 100.3 秒）。结果很差：真值只有 7 次切换，引擎做了 17 次，逐帧准确率只有 66.4%。根因不是阈值没调好，而是**特征本身失去了区分度**：按真值分组，停站抖动中位 1.40、运行 1.97，只差 1.41 倍（09-11 那趟是 0.91 对 3.16，差 3.47 倍），停站 P75=2.21 已经盖过运行 P25=1.30，两个分布基本重叠，29.7% 的帧落在 1.2~2.0 的模糊带里（09-11 是 18.2%）。同一趟麦克风通道同样是重叠的（停站 P75 0.00146 > 运行 P25 0.00131，模拟准确率 57.4%，比磁场还低），所以这不是"该退回麦克风"，是两个通道一起失效。
- **污染源：手机接了有线充电宝**。干扰机理不是磁吸，而是充电电流自身的磁场加上开关电源纹波，且电流随充电状态变化。数据佐证：`magnet_magnitude_ut` 中位数 81.3 µT（09-11 是 40.4），地磁正常范围约 25~65 µT，这趟 68.4% 的帧落在范围外（09-11 为 27.2%），`magnetic_disturbance` 标记为"可能受干扰"的占 32.4%（09-11 为 8.7%），`compass_calibration` 多数处于"受干扰/不可靠"。按 15 秒看 |B|，前两分钟还在 40~67，从约 135 秒起一路抬到 85~148。**但不能把失败全归给充电宝**：按 120 秒切开看，前半段 |B| 中位仅 45.2 时准确率就已经只有 68.7%、区分度 1.15 倍（比后半段还差），说明这条线/这次摆放本身可能也偏弱，两个因素在这份数据里分不开。另外这趟 `app_in_foreground` 占 86.1%（09-11 仅 26.7%），手持看屏幕会给磁场读数额外引入动作噪声，是第二个未受控变量。
- **暴露的结构性问题**：校准在第 16 秒就锁定"可用"（观测 P90=2.49，勉强越过 2.0；09-11 是 4.20），而干扰约在 135 秒才起来——一次性判定加全程锁死，使得环境中途变坏时完全没有察觉和降级的能力，和 GPS "一次定终身"是同一个毛病。另外校准判据只检查"分布横跨判定带"，不检查"两个状态能否分开"，这次放行了一趟实际不可用的数据。加余量要求或中途复查都是候选方案，但目前只有两趟对照数据，暂不据此定新阈值。
- **已试过但不采用**：把抖动换成相对值（Δ|B| / |B|，对磁场直流偏置免疫）在 09-12 能把区分度从 1.41 倍提到 2.02 倍，但仍然重叠救不回来，而且在 09-11 反而从 3.47 倍降到 2.72 倍，因此不改。
- **下一步**：先在同一条线、同样的手机摆放、不接充电宝的条件下重测一趟做对照，把"充电宝干扰"和"该线信号本来就弱"分开，再决定是否改判定逻辑。

## 双通道分位融合（2026-09-12）

判定逻辑换成了磁场与气压的**分位融合**，替代此前的单通道阈值路线。GPS 的优先级不变，仍然在校准通过时压过一切。

**为什么换。** 历史数据里有 6 趟带人工标记的真值（2026-08-17 至 09-12），足以做留一交叉验证：每一折在其余 5 趟上选超参、在留出的那趟上打分。三件事因此定了下来：一是任何单通道配固定阈值都不够稳（磁场留出均值 88.2% 但最差只有 73.7%，麦克风 84.6%/62.0%，气压 82.2%/71.5%）；二是问题不在阈值而在特征的绝对尺度会漂移，同一台手机停站时的磁场抖动中位数在 0.71 到 2.14 之间变动，且**同一趟车内部也在漂**（某趟三次停站分别是 0.71、1.40、2.14），所以一次性校准无论标注多准都会过拟合到第一站；三是把每个通道换成它在最近一段时间里的**分位**（0~1）之后，尺度问题自动消解，因为它只回答"相对于最近一分半，现在算低还是高"。

**分位归一和融合必须配套。** 单通道用分位归一反而更差（磁场从 88.2% 掉到 78.7%），归一化本身会引入噪声；它换来的是几个通道量纲一致、可以直接平均，而平均又把噪声消掉。拆开任何一半都拿不到收益。

**为什么是磁场+气压而不是三通道。** 第一轮扫参的参考实现给麦克风喂的是原始 RMS，结论是三通道最好。把参考实现改成与 InferenceEngine.kt **逐位一致**（同样的下中位数、同样的时间窗、同样剔除 `mic_valid=0` 的帧）之后重扫，结论翻转：真实引擎会丢弃无效的麦克风采样，留下的通道有空洞，拖累平均值。留出成绩为磁场+气压 92.7%/最差 85.2%，三通道 89.7%/75.9%，磁场+麦克风 87.9%/78.2%，麦克风+气压 86.6%/65.6%。而且磁场+气压这一组有 5/6 折选中同一套超参，三通道那组则选不一致，这是第二个偏向它的理由。麦克风的分位仍然每帧计算并写进 CSV，只是通常不进平均，两个主通道有任何一个读不到时它会顶上。

**实装后的复核**（用真实引擎回放那 6 趟）：均值 93.1%、最差 87.6%，切换次数与真值几乎完全吻合（14/14、7/7、5/5）。原先在实地失败的两趟，从实测的 66.4% 和 79.5% 变成 90.5% 和 87.6%。注意 93.1% 是选定超参后的复核值，**留一交叉验证给出的 92.7%/85.2% 才是对新数据的诚实预期**。

- 参数：`FUSION_RANK_WINDOW_MS = 90000`、`FUSION_STOP_SCORE = 0.30`、`FUSION_MOVING_SCORE = 0.65`、确认 5000/3000ms。
- 开关：`FUSION_ENABLED_DEFAULT = true`。关掉即回落到之前的磁场主判/麦克风主判路径，方便对照。
- 新增 CSV 字段：`magnet_rank`、`mic_rank`、`pressure_rank`、`fusion_score`、`fusion_channel_count`、`fusion_stop_candidate_elapsed_ms`、`fusion_moving_candidate_elapsed_ms`、`fusion_enabled`。
- 仍需注意：6 趟依然偏少，其中 2 趟的真值是按"广播交替"假设推的，`0818-1618` 那趟几乎全程单一状态、信息量很低。这是"值得实装并继续实测"的程度，不是定论。

## 停站/运行标记按钮（2026-09-12）

把早期版本有过、后来被"广播"按钮取代的状态标记按钮加了回来。两者用途不同且都需要：`广播N` 是一次性时间戳，用来核对到站提示音；`停站`/`运行` 是**会一直保持到下次改变**的状态标签，因此整趟车每一帧都带着已知答案，可以直接统计准确率。上面那套融合参数正是靠 6 趟这样标注的数据扫出来的。用法是列车停稳时按「停站」、起步时按「运行」。

## 耗电统计（2026-09-12）

新增 `BatteryCollector`，每帧记录电量百分比、电荷计数器、瞬时电流、电池温度、是否在充电与充电方式，以及本次采集的累计消耗。

有一点必须说清楚：**Android 没有让应用测量自身耗电的受支持接口**，这里记录的全部是整机数据，包含屏幕和其他应用。它依然值得记，因为采集途中本应用基本是唯一的负载，而这些数字的用途是在条件相近的前提下**横向比较不同配置**（开不开麦克风、开不开 GPS）。只有屏幕点亮时间相近的两趟之间比较才公平，所以 `app_in_foreground` 和 `screen_on` 就在这些列旁边。

另外**电荷计数器才是可信的测量，百分比不是**：`BATTERY_PROPERTY_CAPACITY` 以整数百分比跳变，15 分钟的采集经常只掉 1 个点甚至 0，而 `CHARGE_COUNTER` 以微安时为单位，分辨率高得多。看 `battery_session_used_mah`，把 `battery_session_drain_pct_per_hour` 当粗略校验即可。充电状态下则根本无法测量消耗（计数器会上升而不是下降），所以 `battery_charging` 一并记录，事后可以把这些时段排除而不是稀里糊涂地平均进去——09-12 那两趟接着充电宝，正属于这种情况。

顺带一提，融合已经不依赖麦克风，所以后续如果确认麦克风通道确实可以不要，关掉录音会是一个明确的省电项，届时可以用这组新字段直接量出省了多少。

## 气压通道与观测补齐（2026-09-12）

2026-09-12 两趟数据（第一次有标记真值）逼出来的两个结论。

**一、固定阈值确实不通用，但"一次性校准期"救不了。** 同一台手机，停站时磁场抖动的中位数在 0.71~2.14 之间变动，固定的 1.2/2.0 不可能通用，这一点是成立的。但拿真实数据试了三种自适应方案，都打不过固定阈值：无标注的一维 Otsu 聚类（09-12#1 磁场 61.7%、09-12#2 51.2%）、**用地面真值当标注**做的校准（43.1% / 73.1%）、以及最近 2~5 分钟分位数的滚动自适应（66.8% / 87.1%），而固定阈值是 75.4% / 79.5%。失败的原因有两层：其一，同一趟车里状态特征本身在漂移（09-12#2 三次停站的抖动中位是 0.71 → 1.40 → 2.14），拿第一次停站校出的阈值对后面两次必然失效，靶子在动，一次性校准无论标注多准都会过拟合到第一站；其二，运行状态自身的内部波动和停站/运行之间的差别一样大，所以无标注聚类会把运行分布的下半截误当成停站（09-12#2 在 66 秒"检测到双峰"，给出低簇 2.23，而真实停站中位是 1.18）。结论是问题不在阈值而在特征：磁场抖动的绝对尺度取决于环境电磁强度，趟间趟内都在变。

**二、气压变化率是目前最有希望的第三通道。** 把已记录的各特征对真值算区分度，气压的一阶差分（平滑后）明显领先：停站与运行的中位数相差 2.43 倍 / 7.16 倍，而磁场抖动是 1.45 / 2.06 倍、麦克风 RMS 是 1.50 / 1.80 倍；单独拿一个固定阈值去跑状态机，气压得到 84.5% / 87.2%，磁场 75.4% / 79.5%，麦克风 69.6% / 87.8%。更关键的是气压是**唯一在磁场被充电宝污染那趟仍然胜出**的通道，说明它的失效场景和另外两个不重叠——物理上也讲得通，隧道里列车像活塞推动空气，停下就平静，这个机制不受电磁干扰也不受车厢噪音影响。气压计本来就一直在采（`pressure_active` 全程为 1），不需要改采集。

本次改动**只做观测，不改判定逻辑**：气压通道算出来写进 CSV，但不参与 `train_state`。原因是它的绝对尺度同样会漂移（2026-09-11 停站时约 0.0175，09-12 约 0.0038），固定阈值一样会翻车，而带真值的数据只有两趟，据此定阈值就是拿两个点画直线。

**顺带补齐了一个观测盲区**：磁场通道用的阈值此前完全没有写进 CSV，导致 09-12 的日志无法判断当时跑在固定阈值还是学习到的动态阈值上。补上之后立刻有收获——09-12#2 那趟磁场有 80% 的时间在用动态阈值，有效停站阈值一路漂到 0.74~1.21，而那两次漏掉的停站抖动分别是 1.40 和 2.14，动态机制当时正在往下追第一站的低值，等于反向加剧了漏判。

- 新增 CSV 字段：`pressure_change_rate`、`pressure_change_rate_smoothed`（每帧气压变化量，及其 4 秒窗口中位数，窗口与 `magnet_jitter_smoothed` 完全一致以便直接对比）、`magnet_dynamic_stop_threshold`、`magnet_dynamic_moving_threshold`、`magnet_effective_stop_threshold`、`magnet_effective_moving_threshold`、`magnet_threshold_mode`。
- 判定配置保持不变：仍然是麦克风关闭、磁场主判（`MIC_DECISION_ENABLED_DEFAULT = false`、`MAGNET_PRIMARY_ENABLED_DEFAULT = true`）。
- 下一步：多跑几趟带标记的数据把真值样本从 2 趟提到 5~6 趟，再决定气压是单独当主判、还是和麦克风/磁场做按帧质量加权的融合。

## GPS 位准（2026-09-06）

麦克风和磁场终究都只是"运动噪音"的间接代理，真正能直接量出车速的只有 GPS。但地铁大半程在地下没有信号，把 GPS 做成硬性依赖会让应用在地下完全失效，所以设计成"先测精度、测过了才用"的可选信号，而不是像麦克风那样时刻参与判定：

- **一次性校准测试**：每次开始录制后的头 `GPS_CALIBRATION_WINDOW_MS`（20 秒）是校准窗口。这段时间里持续收集 GPS 定位的 `accuracy`（米），窗口结束时结算一次：定位样本数达到 `GPS_CALIBRATION_MIN_SAMPLES`（5 个）、且其中精度 `<= GPS_ACCURACY_THRESHOLD_M`（20 米）的样本占比达到 `GPS_CALIBRATION_MIN_GOOD_RATIO`（60%），才判定 GPS "可用"；否则判定"不可用"（地下几乎全程无定位是最常见的不可用场景，样本数直接是 0）。这个判定这趟车只做一次，之后不会再重新测试——如果一趟车前段没信号、后段浮出地面重新有信号，本版本不会中途捡回来（目前只针对开局就有信号的地面轻轨这类场景，如果后续数据显示"中途恢复"值得处理，再补）。
- **判定权限**：一旦判定"可用"，GPS 速度就成为 `train_state` 的唯一判据，麦克风/磁场那一整套融合逻辑全部跳过（但两者仍然继续计算并写入 CSV，方便对照）；一旦判定"不可用"，则完全按之前的麦克风/磁场逻辑运行，就当 GPS 不存在。这是"不强制运行"的含义：GPS 只在证明自己够准的车次里接管，其余车次不受任何影响。
- **速度判定**：GPS 速度 `<= GPS_STOP_SPEED_MPS`（0.5 m/s）记为停站候选，`>= GPS_MOVING_SPEED_MPS`（1.4 m/s）记为运行候选，中间地带保持现状。候选需持续满 `GPS_STOP_CONFIRMATION_MS`（2 秒）/`GPS_MOVING_CONFIRMATION_MS`（1.5 秒）才真正切换状态——比麦克风的对应确认时长（3 秒/1.75 秒）略短，因为 GPS 速度是直接测量而非噪音代理，理论上更不容易抖动，但这组数值还没有真实 GPS 数据验证过，后续按实地测试结果调整。
- **定位丢失**：判定"可用"之后如果某个 tick 拿不到新定位（比如短暂进隧道），会保持上一次 GPS 确认的状态不变，不会退回麦克风判定——如果以后发现有路线会长时间中途失去信号，这里需要重新设计一个中途回退机制，本版本还没做。
- CSV 新增字段：`gps_speed_mps` / `gps_accuracy_m`（当 tick 定位有效时的原始值，否则为空）、`gps_fix_age_ms`（当前定位距上次更新过了多久，超过 5 秒视为无定位）、`gps_calibration_status`（`校准中`/`可用`/`不可用`）、`gps_candidate_state`（GPS 通道自己的候选方向，只有"可用"时才非空）、`gps_stop_candidate_elapsed_ms` / `gps_moving_candidate_elapsed_ms`（GPS 候选已确认计时多久）。
- 权限：需要 `ACCESS_FINE_LOCATION` 才能订阅 `GPS_PROVIDER` 的连续定位——仅有粗略定位权限（原本给罗盘真北用的那个）只能订阅 `NETWORK_PROVIDER`，精度通常几十到几百米，几乎不可能通过校准测试。拒绝精确定位权限不影响其余功能，校准测试自然会判定"不可用"。
- **后台定位限制（2026-09-06 实地测试发现）**：一趟 878 秒的地铁实测里，`app_in_foreground=0`（切到后台/锁屏）的采样点占了约三分之二，这些采样点里 `gps_fix_age_ms` 中位数高达 68.8 秒（前台时中位数只有 0.44 秒），`gps_speed_mps` 非空比例从前台的 79% 掉到后台的 7%——GPS 更新基本停摆，最长一段后台期间（227 秒）定位年龄一路涨到 221.8 秒都没有新定位。原因是 Android 从 10 开始，只有前台使用中的应用才能收到持续 GPS 更新；即使有前台服务在跑，也只有该前台服务本身声明了 `location` 类型、并且应用持有 `ACCESS_BACKGROUND_LOCATION` 权限时，才会被系统豁免这个限制——本版本之前两者都没做（`RecordingService` 的前台服务类型只声明了 `microphone`），所以只要用户切走 app 或锁屏，GPS 就形同虚设。
  - 修复：`RecordingService` 的 `foregroundServiceType` 改成 `microphone|location`（仅在已授予任一位置权限时才在 `startForeground` 里附带 `FOREGROUND_SERVICE_TYPE_LOCATION`，避免没给权限时因为声明了用不了的类型而抛异常），并新增 `ACCESS_BACKGROUND_LOCATION`/`FOREGROUND_SERVICE_LOCATION` 两个权限。但 `ACCESS_BACKGROUND_LOCATION` 从 Android 11 开始不能再跟其他定位权限一起弹一个运行时对话框申请——系统会直接忽略这部分请求，必须引导用户去系统设置里手动把定位权限从"仅使用时允许"改成"始终允许"。因此界面加了一个"位置设置（后台 GPS）"按钮直接跳转本应用的系统设置页；开始采集时如果精确定位权限已给但后台定位权限没给（且系统版本 >= Android 11），会弹 Toast 提示用户点这个按钮手动开启。
  - 这个修复还没有实地验证过（写下这段文档时还没有新的一趟数据），下次测试时应该重点看新版本里后台期间 `gps_fix_age_ms` 是否还会像之前那样一路涨上去。

## 麦克风可靠性

- 录音时通过 `AudioRecord.preferredDevice` 强制指向手机内置麦克风（`AudioDeviceInfo.TYPE_BUILTIN_MIC`），避免连接了蓝牙耳机、有线耳机等带麦克风的配件时被系统自动路由过去——那样采到的车厢噪音会完全失真。找不到内置麦克风设备或平台拒绝该提示时静默忽略，退回系统默认路由。CSV 的 `mic_input_device` 字段会显示实际生效的设备名和类型（比如"内置麦克风"），可以用来确认是否生效。
- RMS 小于 `0.000001` 的样本立即禁止参与状态切换和动态历史。
- 近零持续 2 秒后写入 `mic_valid=0` 和 `mic_quality=全零异常`。
- 恢复非零音频连续 1 秒后重新有效。
- 异常持续时 AudioRecord 最早每 15 秒安全重启一次，并记录 `mic_restart_count`。
- 若 `audio_client_silenced=1`，说明 Android 因后台或并发录音策略主动静音客户端；此时保持列车状态且不反复无效重启。
- 若未被系统静音但持续零 PCM，连续两次这样的重启才会从 `UNPROCESSED` 回退到普通 `MIC` 音源（第一次先原地重试）。这是 2026-09-02 实地测试发现的真实 bug 修复：戴耳机切到别的 app 触发了一次 Android 音频焦点丢失导致的短暂零 PCM，之前的逻辑一次失败就永久切到 `MIC` 音源，而 `MIC` 和 `UNPROCESSED` 在同一台设备上的 RMS 量级可以差出约 100 倍——切换后所有阈值全部失真，那趟车切换之后的所有采样点全部被判成"运行"，直到录音结束都没能再切回"停站"，哪怕列车真的停了。除了给 `UNPROCESSED` 一次重试机会，音源一旦真的发生变化（`audio_source` 字段前后不一致），也会自动重置判定引擎的历史和动态阈值，避免继续沿用旧量级校准出来的阈值。
- `audio_samples_read` 与 `audio_zero_sample_ratio` 用于区分“没有读到数据”和“确实读到了全零 PCM”。
- CSV 同时记录录音 session、音源、read 返回值/错误、活跃录音配置数、路由变化和重启原因。

## 罗盘辅助

- 无位置权限或无可用最近位置时显示磁北；有位置数据时使用 Android 磁场模型换算真北。
- 方向按北、东北、东、东南、南、西南、西、西北显示，并对跨越 0° 的读数做环形平滑。

- 磁场强度超出约 20–100 μT 时标记“可能受干扰”。地铁车厢、轨道和电机附近磁干扰较强，罗盘只作为辅助，不参与列车运行/停站判定。
- CSV 追加磁北、真北、当前采用方位、方向、参考北、来源、精度、校准、磁偏角、位置年龄和磁场干扰字段。
## 后台采集

采集会话由 `RecordingService` 持有。Activity 关闭或屏幕关闭不会停止采集；通知、麦克风、传感器和 WakeLock 仅在用户点击“停止”或服务被销毁时释放。

## 手机游戏联动

`GameLinkServer` 在本机回环地址 `127.0.0.1:8765` 起一个纯 TCP 服务，把每个 250ms tick 的判定结果广播成一行 JSON（换行分隔，无握手、无 WebSocket 帧），同机的另一个 app（比如用 Godot 写的伴生游戏）连上这个端口按行读取即可，不需要 Android 原生插件或 AIDL。这个 socket 跟着 `RecordingService` 的生命周期起停（app 启动就监听），但只有点了“开始采集”之后 tick 循环才会真正广播数据。

字段：

```json
{"v":1,"t":12345,"state":"运行","train_moving":true,"player_active":false,"mic_level_ratio":1.23,"accel_rms":0.05,"gyro_rms_deg_s":2.1}
```

- `v`：协议版本号，当前为 `1`。
- `t`：本次采集会话内的已过毫秒数（`elapsedRealtime` 基准，见上文“状态判定”）。
- `state`：`校准中` / `运行` / `停站` / `停站但玩家活动`。
- `train_moving`：`state` 是否为“运行”的布尔简化版，方便游戏端不用做字符串比较。
- `player_active`：玩家活动判定（加速度或陀螺仪超阈值）。
- `mic_level_ratio`：麦克风 RMS 相对当前停站/运行阈值中点的比例，可用作强度/难度的连续信号。
- `accel_rms` / `gyro_rms_deg_s`：本 tick 内的加速度计、陀螺仪 RMS 原始值。

连接是尽力而为、非阻塞的：没有客户端连接时不产生任何开销；客户端断开或写入失败会被静默清理，不影响采集本身。多个客户端同时连接会收到相同的广播。
